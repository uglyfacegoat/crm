## Итоговая оценка

Текущий код — не одноразовый макет. В нём есть продуманная модель данных, серверная авторизация, доменные модули, транзакции, аудит и заметный набор автоматических проверок. Основа выглядит уверенно для внутренней beta/пилота.

Оценка:

- **7.2/10 как кодовая база внутреннего продукта**;
- **5.5/10 как готовая публичная mission-critical система**.

Разница связана не с плохим кодом функций, а с отсутствующими эксплуатационными слоями: CI/CD, централизованной наблюдаемостью, внешними резервными копиями, масштабируемым файловым хранилищем и полноценными сценариями отказа.

## Объём и структура

На момент аудита:

- 327 TypeScript/TSX-файлов в `src`;
- около 42 310 строк TypeScript/TSX в `src`;
- 51 миграция БД;
- 70 файлов тестов и проверок в `src` и `scripts`;
- Next.js 16, React 19, PostgreSQL 17;
- 0 известных production-уязвимостей по `npm audit --omit=dev` на момент проверки.

Архитектура представляет собой модульный монолит: App Router, серверные страницы/actions, клиентские workspace-компоненты, доменные server-модули, PostgreSQL и отдельные фоновые процессы в Docker Compose.

## Что сделано качественно

### Серверная модель

Модули разделены по бизнес-областям: auth, clients, orders, visits, tasks, contracts, documents, finance, chat, sites и аналитика. Репозитории, схемы и типы в основном находятся рядом с доменом. Это лучше горизонтальной архитектуры, где вся бизнес-логика смешана в общих controllers/services/utils.

### Границы доверия

Внешние данные валидируются через Zod, SQL параметризован, разрешения проверяются на сервере. В коде не обнаружено систематического использования `any`, `@ts-ignore` или небезопасного подавления ошибок типов. Это сильный показатель дисциплины.

### Авторизация

Есть разделение authentication и authorization, роли, разрешения и ограничения по организации. Сессия не хранится в БД в открытом виде. Операции защищаются серверными проверками, а не только скрытыми кнопками.

### Целостность данных

Используются транзакции, связи, уникальность, оптимистические проверки и идемпотентность. Финансовая история не уничтожается обычным удалением. Документы имеют версии и hashes. Эти решения важнее внешней «чистоты» кода, потому что предотвращают тихую порчу бизнеса.

### Тестовый контур

Помимо unit-тестов есть flow-check сценарии для авторизации, заказов, договоров, финансов, уведомлений, backup, сайтов, компаний, поддержки, чата и UI. Отдельные visual/UI audit сценарии проверяют маршруты, переполнение, доступные имена кнопок и адаптивность.

### Зависимости

Набор библиотек умеренный. Для базовых задач не установлены несколько конкурирующих UI-фреймворков или state managers. Это уменьшает bundle, конфликт паттернов и стоимость обновлений.

## Важные проблемы

### IMPORTANT — крупные клиентские компоненты

Несколько файлов уже имеют 700–1500 строк, включая календарь, быстрое оформление, финансы, документы, навигацию и задачи. Это увеличивает связность, усложняет тестирование и провоцирует лишние rerender/effect зависимости.

Исправление не должно быть механическим «разбить на десять компонентов». Следует выделять устойчивые ответственности:

- контроллер состояния экрана;
- представление таблицы/календаря;
- фильтры и сериализация query;
- формы и runtime-валидация;
- бизнес-вычисления в чистые функции;
- отдельные диалоги с явными контрактами.

### IMPORTANT — фиксированные лимиты вместо пагинации

Реестры ограничиваются выборками примерно от 200 до 2000 записей. Это безопаснее неограниченной загрузки, но пользователь не может гарантированно добраться до старой записи, а рост создаст тяжёлые запросы. Нужна единая курсорная пагинация, server-side сортировка и виртуализация только там, где она реально требуется.

### IMPORTANT — нет глобальных error/loading boundaries

В App Router отсутствует системный набор `error.tsx`, `global-error.tsx` и `loading.tsx`. Ошибка одного запроса может приводить к грубому экрану и слабой диагностике. Нужны безопасные пользовательские сообщения с correlation ID, сохранение введённых данных и логирование причины на сервере.

### IMPORTANT — чат и оперативные статусы не realtime

Часть интерфейса полагается на обновление/опрос. Для чата, входящих заявок и переносов это функциональная надёжность, а не косметика. Следует выбрать WebSocket или SSE, определить восстановление соединения, порядок событий, дедупликацию и непрочитанные состояния.

### IMPORTANT — файлы привязаны к локальному узлу

Локальное хранение мешает горизонтальному масштабированию и создаёт общий отказ приложения и файлов. Нужен закрытый S3-compatible storage, безопасные имена, тип/размер, antivirus pipeline, signed download и lifecycle policy.

### IMPORTANT — нет CI

Скрипты проверки есть, но репозиторий не содержит workflow, который делает их обязательными. Это означает, что качество зависит от дисциплины запуска вручную. Минимальный merge-gate: install с lockfile, typecheck, lint, tests, build, проверка миграций.

### IMPORTANT — недостаточная наблюдаемость

Нет централизованного error tracking, трассировки запросов, бизнес-метрик и alerting. `console.error` помогает локально, но недостаточен, когда пользователь сообщает «вчера пропала заявка». Нужны request ID, actor/org/entity context без лишних PII и дашборды по HTTP, БД, очередям, backup и интеграциям.

### NOTE — tenant isolation только на прикладном уровне

Фильтрация `organization_id` реализована, но одна ошибочная выборка потенциально имеет большой радиус. При росте multi-tenant нагрузки стоит оценить RLS и автоматические тесты, которые доказывают невозможность доступа между организациями.

### NOTE — конфигурация валидируется не единым способом

Критические переменные стоит проверять при старте одним типизированным модулем. Production не должен запускаться с development-default для security-sensitive параметров.

## Риски регрессий

1. Разные экраны переопределяют один статус или формат даты.
2. Client state копирует server state и расходится после server action.
3. Большой компонент одновременно управляет несколькими диалогами и создаёт скрытые зависимости.
4. Миграция добавляет nullable поле без плана backfill/ограничения.
5. Аналитика повторяет формулы финансов вместо вызова общего доменного расчёта.
6. Файл удаляется физически до проверки ссылок и retention.
7. Permission добавляется в UI, но забывается на server action или repository query.
8. Flow-check зависит от локальных seed-идентификаторов и не ловит реальные граничные случаи.

## План укрепления кода

### Ближайшие 30 дней

- добавить CI merge-gates;
- добавить global error/loading boundaries;
- централизовать env validation;
- внедрить error tracking и request IDs;
- зафиксировать архитектурные границы модулей;
- перевести самые крупные списки на курсорную пагинацию;
- написать отрицательные тесты организации/прав для критических actions;
- настроить offsite backup и restore drill.

### 31–60 дней

- перенести файлы в object storage;
- внедрить realtime транспорт для чата и критичных событий;
- декомпозировать календарь, quick-order, finance и documents по ответственностям;
- ввести единую модель query filters/sort/pagination;
- добавить интеграционные тесты конкуренции назначения и финансовых операций;
- определить SLO и alerting.

### 61–90 дней

- нагрузочно проверить поиск, календарь, аналитику и документы;
- ввести очередь интеграций;
- добавить аудит административных выгрузок;
- оценить RLS и SSO/MFA на основе модели эксплуатации;
- формализовать lifecycle и retention персональных данных;
- провести disaster-recovery упражнение.

## Что не нужно делать сейчас

- не дробить ядро на микросервисы;
- не вводить глобальный state manager без доказанной проблемы;
- не переписывать рабочие repository-модули на ORM ради единообразия;
- не создавать универсальный generic CRUD слой для разных доменов;
- не разносить каждый JSX-блок в отдельный файл без смысловой границы;
- не маскировать ошибки пустыми массивами и placeholder-данными;
- не добавлять AI-автоматизацию до стабильных правил и аудита.

## Критерий «код стоит ровно»

Код можно считать уверенным, когда любой merge автоматически проверяется, любой критичный сбой наблюдаем, любую production-базу можно восстановить, любое важное действие имеет серверную авторизацию и аудит, а реестр не зависит от скрытого лимита. Сейчас функциональный фундамент близок к этому состоянию, эксплуатационная часть — ещё нет.
