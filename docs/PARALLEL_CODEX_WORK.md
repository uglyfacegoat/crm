# Два параллельных потока для CRM

Старт: 24 сентября 2026. Базовый локальный коммит: `20f9e90`. Эта версия содержит 17 локальных коммитов, ещё не отправленных в GitHub по просьбе владельца. Оба потока работают от неё. Закрыто 11/197 пунктов; число галочек меняется только после проверки результата.

## Разделение

| Поток | Пункт и результат | Основные файлы | Условие готовности |
| --- | --- | --- | --- |
| Первый Кодекс, основная папка `crm` | `PERF-01`: продолжить аудит скрытых лимитов и устранять те, которые делают данные недоступными в формах/реестрах. Текущий статус и уже исправленные места — `docs/LIST_LIMIT_AUDIT.md`. | Реестры, формы выбора, `docs/LIST_LIMIT_AUDIT.md` | Данные за прежним лимитом доступны через поиск/страницы; тесты на количество больше лимита и разделение компаний. `PERF-01` не закрывать только за одну исправленную форму. |
| Второй Кодекс, отдельная папка `crm-codex-2` | `UP-01`: проверить все пути загрузки на серверный размер, MIME и сигнатуру, расширение и генерируемый ключ; исправить доказанные пробелы. Карта путей — `docs/STORAGE_WRITERS.md`, периметр — `docs/UPLOAD_PERIMETER_MATRIX.md`. | Upload actions/routes, файловая валидация, отдельный отчёт `docs/UPLOAD_VALIDATION_AUDIT.md` | Для каждого типа файла есть разрешённые форматы, предел до чтения в память, серверная проверка содержимого и безопасный путь хранения. Негативные проверки покрывают подмену MIME/расширения, слишком большой файл и обход через альтернативный upload-путь. Если часть требований зависит от `UP-02` (сканирование опасного содержимого), явно отделить её и не отмечать `UP-01` закрытым без собственной приёмки. |

Оба потока читают `AGENTS.md` и нужные локальные руководства Next.js перед изменением Next-кода. Первый не редактирует загрузки, второй не редактирует реестры и формы выбора. Второй не меняет `PEREDVIDEOPOKAZOM/END_PRODUCTION_PLAN.md`, `.github/workflows/crm-ci.yml` и общий `package.json` без необходимости; если изменение нужно, указывает его в отчёте, а интеграцию делает первый поток. Не запускать два теста одновременно против одной постоянной БД и не менять текущие данные Docker. Интеграционные тесты — на одноразовой БД. Коммиты локальные; не делать `git push`, deploy или обновление Docker.

## Передача результата

1. Второй Кодекс сохраняет завершённую часть одним или несколькими локальными коммитами в своей ветке и сообщает hash, проверки и открытые ограничения.
2. Первый проверяет diff и переносит коммиты в основную ветку. Конфликты разрешает в основной папке, затем запускает проверки затронутых функций и сборку.
3. После приёмки первый обновляет отметки в END-плане и общую цифру закрытых пунктов. Пуш в GitHub только после отдельной команды владельца.
