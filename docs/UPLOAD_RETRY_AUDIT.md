# Повторы и неопределённый результат загрузок (UP-07, в работе)

24 сентября 2026. Девять пользовательских потоков перечислены в [карте записи файлов](STORAGE_WRITERS.md). `UP-07` пока открыт: обрыв уже начатого браузерного запроса до commit ещё не проверен для восьми остальных семейств. Для нового документа проверены оба исхода — commit и rollback.

Что подтверждено сейчас:

- `scripts/upload-commit.check.mjs` проверяет документ, версию, чек оплаты и чек выплаты. При ошибке после подтверждённого commit файл остаётся и интерфейс сообщает о сохранении с требованием обновить страницу. При известном отказе откатывается только принадлежащий запросу файл; при неизвестном исходе байты сохраняются до сверки. Повтор уже подтверждённой операции не читает и не записывает файл снова.
- `scripts/upload-lifecycle.check.mjs` проверяет акт, фото выезда, шаблон, вложение и фото группы на те же исходы commit/отказа, `EEXIST` и сохранение прежнего фото группы. Для первых четырёх дополнительно подтверждено, что повтор принятого запроса не читает и не записывает файл снова. Текущие проверки используют управляемые подмены репозитория и файлового адаптера.
- `scripts/uploads-browser-check.mjs` на собранном сервере проходит все девять потоков с нормальным сохранением и с ошибкой обновления интерфейса после commit. Два одинаковых Server Action POST одновременно проверены для всех девяти потоков: по одной ожидаемой записи и версии файла, правильные байты; прежняя версия документа остаётся доступной, выезд завершается один раз. Ответы возвращают успех либо сообщение об обработке/конфликте. Все эти сценарии прошли с локальным и тестовым S3-хранилищем. Отдельные проверки потери ответа БД на COMMIT описаны ниже.
- При перегрузке двух слотов обработки браузер получил ошибку до записи и сохранил idempotency key. Формы нового документа и новой версии сохранили название/комментарий и выбранный файл: после освобождения слотов повтор без повторного заполнения успешно сохранил один документ и ровно по одной записи каждой версии.
- Чек оплаты и чек выплаты также проверены при занятых слотах: отказ не создал финансовую запись или документ, а формы сохранили ключи, сумму, реквизиты, комментарий и файл. Повтор после освобождения слотов создал по одной финансовой записи и одному чеку с проверенными байтами.
- Фото выезда и подписанный акт проверены под учётной записью мастера. При занятых слотах отказ не создаёт документ и не завершает выезд; формы сохраняют ключи, комментарии, название акта и выбранные файлы. После повтора оба файла сохранились по одному разу, выезд завершился, байты совпали.
- Шаблон, вложение сообщения и фото группы также прошли отказ при занятых слотах и повтор на собранном сервере. Шаблон и группа сохранили файл и текстовые поля; существующая защита черновика чата сохранила текст, файл и ключ сообщения. До повтора записи не появились, после повтора каждая запись и её файл появились один раз, байты совпали. Таким образом сохранение полей при этом конкретном исправимом отказе проверено для всех девяти потоков.
- Для всех девяти потоков браузерный тест потерял ответ **после** успешного Server Action commit. Формы сохранили файл и поля, показали сообщение о проверке результата. Повтор исходного POST и отправка из интерфейса оставили по одной ожидаемой записи и версии файла с правильными байтами; у нового документа остались обе версии, в чате — одно сообщение с одним вложением, подписанный акт завершил выезд один раз. У фото группы оба повтора распознали уже сохранённый запрос без замены файла. Все девять сценариев прошли с local и тестовым S3. До исправления обрыв при новом документе открывал общий экран ошибки и закрывал форму.
- Все девять потоков на собранном сервере с local и тестовым S3 прошли реальную потерю **подтверждения PostgreSQL COMMIT**: тестовый прокси пропустил каждый COMMIT в БД и оборвал соединение до ответа. Формы сохранили файлы и поля, показали неопределённый результат. Независимое соединение подтвердило соответствующие документы, версии, финансовые записи и суммы, сообщение, настройки группы, завершение выезда и байты файлов. Повторы не создали дублей и не удалили неразрешённые строки `file_write_operations`; фото группы теперь распознаёт свой уже сохранённый запрос. Это отдельный случай от потери HTTP-ответа **после** успешного Server Action commit.
- Для нового документа браузерный запрос также оборван **до отправки на сервер**. На local и тестовом S3 форма сохранила поля, файл и ключ; до повтора документ отсутствовал в БД (на local также отсутствовал файл), повтор создал одну версию с правильными байтами. Это не моделирует обрыв уже начатой записи.
- Для нового документа отдельно проверен обрыв **уже начатого** POST до commit. Тестовый триггер одноразовой БД остановил транзакцию после записи файла на вставке версии документа: отдельное соединение не видело документ, файл уже лежал в local/S3. Браузерный запрос оборван, форма сохранила ключ, название и файл; после освобождения БД сервер завершил транзакцию. Повтор из формы нашёл одну версию без дубля, байты совпали. Оба хранилища прошли.
- Для того же потока отдельно проверен **rollback после обрыва**: после записи файла и отмены браузерного POST завершён процесс ожидающей транзакции PostgreSQL. Документ и версия не появились, но файл и неразрешённая запись `file_write_operations` сохранились в local/S3. Форма удержала ключ, название и файл; повтор не присвоил себе неопределённые байты и не удалил их. Вместо обещания, что запрос ещё обрабатывается, интерфейс предлагает проверить архив и обратиться к администратору. Автоматического восстановления этого исхода нет: требуется сверка и ручное разрешение операции по [инструкции](FILE_WRITE_DRAIN.md). В обоих прогонах после принудительного завершения соединения БД сервер также записал `uncaughtException` (`Cannot read properties of null (reading 'write')`). Стек указывает на отложенную запись в сокет библиотеки `postgres` 3.4.9 после закрытия сокета. Это совпало с [открытым исправлением upstream](https://github.com/porsager/postgres/pull/1168); ниже описан проверенный локальный патч.

Особый случай фото группы: запрос опирается на версию настроек канала. При сохранении фото в той же транзакции записывается ключ запроса. После потери ответа повтор признаётся своим только при совпадении ключа, автора, версии, названия, описания, персонального mute и ключа/checksum/размера/MIME файла. Изменённое название с тем же ключом, другой ключ или другой файл сохраняют конфликт. Браузерные local/S3-прогоны подтвердили один аватар и одну версию настроек без замены файла; интеграционный тест проверил несовпадения и последующее изменение группы. Старые фото без ключа повтора не признаются, что безопасно для уже сохранённых данных.

Для закрытия `UP-07` осталось воспроизвести оба исхода обрыва уже начатого запроса до commit для остальных восьми потоков на настоящем runtime с одноразовой БД; сверить таблицы, версии и байты файлов после повторов. В неизвестном исходе нельзя удалять файл только потому, что клиент не получил ответ.

Для наблюдавшейся ошибки `postgres` 3.4.9 применена ровно одна строка из [upstream PR](https://github.com/porsager/postgres/pull/1168): `postinstall` проверяет версию и ожидаемый исходный код, затем добавляет защиту от записи в закрытый сокет в ESM и CommonJS. Новых зависимостей нет. Чистая `npm ci`, Docker-стадия зависимостей и повторные полные браузерные прогоны с local/S3 прошли; тест теперь отклоняет прежнее исключение и проверяет, что процесс жив после разрыва БД. Патч следует убрать после выхода и проверки официального исправления. Другие сценарии отказа БД и нагрузка этим тестом не покрыты.
