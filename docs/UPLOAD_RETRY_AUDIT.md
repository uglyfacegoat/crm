# Повторы и неопределённый результат загрузок (UP-07, в работе)

24 сентября 2026. Девять пользовательских потоков перечислены в [карте записи файлов](STORAGE_WRITERS.md). `UP-07` пока открыт: проверок двойной отправки, отмены браузерного запроса и потерянного ответа на настоящем runtime/БД для каждого семейства ещё нет.

Что подтверждено сейчас:

- `scripts/upload-commit.check.mjs` проверяет документ, версию, чек оплаты и чек выплаты. При ошибке после подтверждённого commit файл остаётся и интерфейс сообщает о сохранении с требованием обновить страницу. При известном отказе откатывается только принадлежащий запросу файл; при неизвестном исходе байты сохраняются до сверки. Повтор уже подтверждённой операции не читает и не записывает файл снова.
- `scripts/upload-lifecycle.check.mjs` проверяет акт, фото выезда, шаблон, вложение и фото группы на те же исходы commit/отказа, `EEXIST` и сохранение прежнего фото группы. Для первых четырёх дополнительно подтверждено, что повтор принятого запроса не читает и не записывает файл снова. Текущие проверки используют управляемые подмены репозитория и файлового адаптера.
- `scripts/uploads-browser-check.mjs` на собранном сервере проходит все девять потоков с нормальным сохранением и с ошибкой обновления интерфейса после commit. Два одинаковых Server Action POST одновременно проверены для нового документа, новой версии, оплаты, выплаты и шаблона: по одной ожидаемой записи и версии файла, правильные байты; прежняя версия документа остаётся доступной. Ответы возвращают успех либо сообщение об обработке/существующем файле запроса. Эти сценарии прошли с локальным и тестовым S3-хранилищем. Фото выезда, закрывающий акт, вложение чата, фото группы и обрыв сети в момент commit этим прогоном пока не покрыты.
- При перегрузке двух слотов обработки браузер получил ошибку до записи и сохранил idempotency key. Формы нового документа и новой версии сохранили название/комментарий и выбранный файл: после освобождения слотов повтор без повторного заполнения успешно сохранил один документ и ровно по одной записи каждой версии.
- Чек оплаты и чек выплаты также проверены при занятых слотах: отказ не создал финансовую запись или документ, а формы сохранили ключи, сумму, реквизиты, комментарий и файл. Повтор после освобождения слотов создал по одной финансовой записи и одному чеку с проверенными байтами.
- Фото выезда и подписанный акт проверены под учётной записью мастера. При занятых слотах отказ не создаёт документ и не завершает выезд; формы сохраняют ключи, комментарии, название акта и выбранные файлы. После повтора оба файла сохранились по одному разу, выезд завершился, байты совпали.
- Шаблон, вложение сообщения и фото группы также прошли отказ при занятых слотах и повтор на собранном сервере. Шаблон и группа сохранили файл и текстовые поля; существующая защита черновика чата сохранила текст, файл и ключ сообщения. До повтора записи не появились, после повтора каждая запись и её файл появились один раз, байты совпали. Таким образом сохранение полей при этом конкретном исправимом отказе проверено для всех девяти потоков. Другие причины отказа и неизвестный исход записи остаются открытыми.

Особый случай фото группы: запрос опирается на версию настроек канала. Повтор с прежней версией после успешного обновления получает конфликт и просит обновить группу; это не дублирует файл, но автоматического распознавания уже принятого повтора нет. Перед изменением поведения нужно сопоставлять сохранённый ключ и checksum, не принимая за свой результат чужое изменение настроек.

Для закрытия `UP-07` осталось воспроизвести двойную отправку в остальных четырёх семействах и обрыв/отмену на реальном runtime с одноразовой БД; сверить таблицы, версии и байты файлов после повторов. В неизвестном исходе нельзя удалять файл только потому, что клиент не получил ответ.
