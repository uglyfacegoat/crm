# Конкурентная обработка файлов — UP-05 (частично)

24 сентября 2026. Загрузка файла уже ограничена 15 МиБ, но разбор PDF/изображений, антивирус и ZIP-экспорт одновременно расходуют память. [Общий слот](../src/server/file-scan/processing-slots.ts) использует два отдельных advisory-lock ключа PostgreSQL: один тяжёлый upload или экспорт занимает один ключ на время проверки и записи либо чтения и сборки архива. Поэтому два web-процесса с общей БД видят один предел. При занятых слотах новая загрузка не создаёт файл/строку БД и показывает сообщение о повторе, экспорт возвращает HTTP 429 с `Retry-After: 3` до чтения файлов и записи audit-события. Слот освобождается после успеха и ошибки.

Тот же слот теперь охватывает проверенное чтение документа и его версий, шаблона, вложения чата и чтение с разбором DOCX для preview. При занятых слотах эти маршруты отвечают HTTP 429 и `Retry-After: 3` до чтения файла; права и лимит запросов проверяются прежде. Из ответа документа и аватара удалена явная дополнительная копия буфера.

ZIP-экспорт теперь отдаёт архив порциями по 64 КиБ и держит общий слот до завершения чтения потока приложением или его отмены. Пятиминутный предел всей передачи прерывает поток и освобождает слот, если он не завершился. При упаковке больше нет полной копии готового ZIP, а при создании HTTP-ответа нет полной копии буфера. Локальный замер Node на буфере 50 МиБ показал около 52 МиБ дополнительной внешней памяти для `new Response(buffer)` и около 2 МиБ при создании потокового ответа; это сравнение механизма ответа, не замер всего приложения под нагрузкой.

25 сентября тот же потоковый ответ применён к скачиванию документа, исторической версии, шаблона и вложения чата, включая частичную выдачу аудио. Слот теперь удерживается до чтения потока приложением, отмены или пятиминутного предела; ответы чата без тела (HEAD, 304, 412, 416) освобождают его до возврата. Полный файл по-прежнему читается, проверяется по размеру и SHA-256 и проходит обязательный сканер до создания ответа. Проверены точные байты, заголовки, аудио-диапазоны, условные запросы, права и аудит.

25 сентября добавлен воспроизводимый локальный профиль `UPLOAD_CHECK_PROFILE_BODY=true UPLOAD_CHECK_RUNTIME=.next/standalone/server.js npm run test:uploads-browser`. Он в одноразовой БД отправляет четыре одновременных multipart-тела по 15 МиБ с заведомо неверным ID Server Action: прокси читает тела, но CRM-действие не выполняется. Два прогона на этом Mac дали RSS веб-процесса 221→298 МиБ и 224→296 МиБ (прирост 77 и 72 МиБ); запросы завершились 404, число документов не изменилось, readiness осталось 200. Пик выбирается опросом `ps` каждые 50 мс, поэтому кратковременный более высокий пик мог быть пропущен. Это измерение конкретного локального процесса после полного браузерного сценария, не ёмкость будущего сервера и не проверка настоящих четырёх загрузок до записи.

В установленном Next.js 16.3.5 `getCloneableBody` создаёт копию тела для прокси до Server Action; существующая проверка 16 МиБ в [`proxy.ts`](../src/proxy.ts) затем читает поток целиком. Общий PostgreSQL-слот внутри действия начинается позже и не ограничивает этот этап. Следующий вариант — допуск до Next через ingress с ограничением параллельных запросов и буфером тела на диске; [Nginx описывает](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_body_buffer_size) перенос тела, превышающего буфер, во временный файл и [ограничение одновременных запросов](https://nginx.org/en/docs/http/ngx_http_limit_conn_module.html). До установки нужно проверить размер временного хранилища, поведение формы при отказе до Server Action и настройки доверенного прокси. Пока это кандидат, а не внедрённая защита.

Проверки: интеграционный сценарий удержал два слота через разные пулы PostgreSQL, третий запрос получил отказ; после освобождения и после исключения слот снова доступен. Отдельный сценарий на PostgreSQL проверил, что слот потокового ответа занят до чтения/отмены, а также освобождается после ошибки подготовки. Браузерный сценарий на собранном сервере удержал оба слота, получил 429 на экспорт и отказ загрузки без записи. Все девять файловых потоков сохранили ключ повтора, поля и выбранные файлы при отказе из-за занятых слотов; повтор без заполнения создал по одной ожидаемой записи с проверенными байтами. Отказ при закрытии выезда не менял его статус. Повторный браузерный прогон проверил 429 для обычного документа, исторической версии, шаблона и вложения чата при занятых слотах, а также обычное скачивание после их освобождения. Отдельный route-тест проверил DOCX-preview при занятых слотах и его корректный разбор при свободных. Эти проверки прошли с local и тестовым S3 на одноразовой БД; рабочие файлы не изменялись.

Ограничение текущего решения: тело запроса уже может быть принято Next.js до получения слота, поэтому параллельные входящие 15-МиБ запросы всё ещё занимают память. Файл целиком читается в память перед передачей, а фактическое поведение потоков при медленном клиенте через реальный сервер/прокси и пиковая память ещё требуют отдельного замера. Не все небольшие чтения (например, аватары) занимают слот. Нет замера RSS, задержек и временных файлов под нагрузкой на выбранном сервере. Значение «два слота» консервативное для кандидатной версии, а не доказанная ёмкость будущего сервера. UP-05 остаётся открытым.
