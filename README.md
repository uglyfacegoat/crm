# CRM сервисной компании

Рабочий прототип CRM для управления клиентами, объектами, заказами, мастерами, выездами и документами.

Подробный статус и порядок разработки находятся в [CRM_ROADMAP.md](./CRM_ROADMAP.md).

## Локальный запуск

```bash
npm install
npm run dev
```

Откройте [http://localhost:3000](http://localhost:3000) в браузере.

## Запуск всей CRM в Docker

Для рабочего локального стенда приложение и PostgreSQL запускаются одним production Compose-стеком. Создайте `.env.local` из `.env.example`, задайте безопасные значения и выполните:

```bash
npm run docker:deploy
```

Команда собирает Next.js в standalone-образ, запускает миграции до старта приложения, пересоздаёт изменившийся контейнер и ждёт зелёных healthcheck приложения и базы. Повторяйте эту же команду после изменений кода — Docker использует кэш неизменившихся слоёв.

Compose также запускает отдельный `reminder-worker`. Он раз в минуту синхронизирует системные сообщения чата и персональный центр уведомлений о выездах следующего дня, выездах без мастера, прошедших выездах без закрывающего акта, просроченных задачах и договорах в окне продления или после срока — независимо от открытия интерфейса. Повторные и параллельные запуски безопасны: PostgreSQL использует advisory lock и уникальные ключи событий, решённые напоминания скрываются автоматически, а heartbeat воркера возвращается в `/api/v1/system/health`. Частоту можно настроить через `REMINDER_WORKER_INTERVAL_MS` в диапазоне от 5 секунд до 1 часа.

Отдельный `backup-worker` раз в сутки создаёт единый комплект PostgreSQL и приватного файлового хранилища в закрытом Docker volume. Архив сначала пишется во временный каталог, затем проверяется SHA-256 и восстанавливается в отдельную временную базу через `pg_restore`; только после успешного чтения обязательных таблиц запуск получает статус `succeeded`. История, размер, heartbeat и факт restore-проверки видны администратору в `Настройки → Система` и в `/api/v1/system/health`. Период, retry и срок хранения задаются `BACKUP_INTERVAL_MS`, `BACKUP_RETRY_INTERVAL_MS` и `BACKUP_RETENTION_DAYS`.

Локальный backup volume не является off-site копией: потеря всего Docker-хоста затронет и рабочие данные, и архивы. Перед production-публикацией нужна зашифрованная репликация комплектов в отдельное S3-compatible хранилище с независимыми ключами доступа.

Повторно проверить последний архив реальным восстановлением можно без остановки CRM:

```bash
npm run backup:restore-check
```

Команда создаёт временную БД с безопасным служебным именем и удаляет её после проверки. Для аварийного восстановления production-данных сначала сохраните копию текущего состояния и выполняйте перенос в новую пустую БД; не направляйте `pg_restore` поверх рабочей базы.

Колокольчик и маршрут `/notifications` читают только персональные события текущего участника организации. Прочтение не влияет на коллег, критичные события имеют отдельный счётчик, а ссылки формируются сервером из типизированной сущности — произвольные URL из базы не исполняются. Загрузка документа или новой версии сразу создаёт уведомления коллегам в той же транзакции.

- CRM: [http://localhost:3000](http://localhost:3000)
- Статус контейнеров: `docker compose --env-file .env.local ps`
- Логи CRM: `npm run docker:logs`
- Остановка без удаления данных: `npm run docker:down`

`AUTH_COOKIE_SECURE=false` допустим только для доверенного локального HTTP-стенда. Перед публикацией в интернет необходимо включить HTTPS, поставить reverse proxy и установить `AUTH_COOKIE_SECURE=true`. PostgreSQL наружу доступен только через `127.0.0.1`, а само приложение внутри контейнера работает от непривилегированного пользователя.

## Локальная база данных

Бэкенд развивается как модульный монолит внутри Next.js на TypeScript с PostgreSQL. Это сохраняет одну типовую систему и один deployment-контур; отдельный Go/Python-сервис имеет смысл выделять только для доказанно тяжёлой интеграционной нагрузки.

Создайте `.env.local` из `.env.example`, замените демонстрационный пароль и выполните:

```bash
npm run db:up
npm run db:migrate
```

Остановить локальный Compose-стек можно командой `npm run db:down`. Данные остаются в именованном Docker volume.

## Авторизация

Для обычной работы над интерфейсом используется явный `AUTH_MODE=preview`: данные демонстрационные, а серверные операции записи не выполняются.

Чтобы проверить реальную авторизацию, клиентский CRUD и основной поток заказов:

1. Установите в `.env.local` `AUTH_MODE=required` и замените `AUTH_THROTTLE_SECRET` длинной случайной строкой.
2. Запустите `npm run db:up` и `npm run db:migrate`.
3. Заполните переменные `AUTH_BOOTSTRAP_*` и один раз выполните `npm run auth:create-admin`.
4. Запустите CRM и войдите созданным e-mail/телефоном и паролем.

Команда bootstrap создаёт новую организацию и администратора транзакционно и отказывается повторно использовать существующий login. Пароль хранится только как scrypt-хеш; session-токен хранится в БД только в виде SHA-256.

Учётная запись мастера всегда привязывается к существующей активной записи справочника. Для создания задайте `AUTH_MEMBER_ORGANIZATION_ID`, `AUTH_MEMBER_MASTER_ID`, `AUTH_MEMBER_NAME`, `AUTH_MEMBER_EMAIL`, при необходимости `AUTH_MEMBER_PHONE`, безопасный `AUTH_MEMBER_PASSWORD`, `AUTH_MEMBER_ROLE=master` и выполните `npm run auth:create-member`. Один профиль мастера нельзя связать с двумя аккаунтами. После входа мастер попадает в `/my-visits` и видит только назначенные ему выезды; офисные списки, глобальный поиск и чужие карточки для этой роли недоступны.

Глобальный поиск открывается через `Ctrl/Cmd + K` и работает через `GET /api/v1/search?q=...`. Он ищет в пределах текущей организации по клиентам и контактам, объектам, заказам, документам, мастерам и выездам; поддерживает телефоны, адреса и полные даты в форматах `ДД.ММ.ГГГГ` и `ГГГГ-ММ-ДД`. Сервер возвращает только типы сущностей, разрешённые роли, а PostgreSQL использует trigram-индексы для поиска по подстроке. Интерфейс отменяет устаревшие запросы, показывает реальные состояния ошибки/загрузки и доступен с клавиатуры и телефона.

Раздел `Оформить` предназначен для администратора и диспетчера на телефоне и компьютере. За четыре шага он находит или создаёт клиента, выбирает контакт, добавляет объект, фиксирует услугу и мастера, назначает первый выезд и выдаёт готовую карточку для отправки. Клиент, контакт, объект, заказ, строки услуг, выезд, история и задача-напоминание записываются одной транзакцией: при любой ошибке частичные данные не остаются. Повторная отправка защищена idempotency-ключом, а пересечения расписания мастера проверяются до записи и ограничением PostgreSQL.

После создания первого администратора новые учётные записи добавляются в `Настройки → Пользователи`. Там администратор назначает роль, связывает роль мастера с активной карточкой справочника, отключает доступ или заменяет временный пароль. При отключении, смене роли, привязки или сбросе пароля сервер отзывает активные сессии сотрудника. Сброс пароля защищён idempotency и optimistic concurrency, а в audit log записывается только факт операции; собственную роль и пароль администратор с этого экрана изменить не может.

Утверждённые формы закрывающих актов загружаются администратором в `Настройки → Шаблоны`. Разрешены проверенные PDF и DOCX до 15 МБ; система не меняет содержимое и юридические реквизиты. Активные формы доступны мастеру в `/my-visits`, а скачивание выполняется только после проверки сессии, роли и SHA-256 файла.

Документы хранят неизменяемую историю версий. Новая версия получает номер на сервере, не перезаписывает предыдущий файл и сохраняет автора, дату, примечание, размер и SHA-256. Загрузка защищена idempotency и optimistic concurrency; текущая и любая историческая версия выдаются только после проверки сессии, tenant-доступа и целостности файла.

Архив документов не создаёт дублирующие физические папки. Он строит логическое дерево `Клиент → Объект → Заказ → Категория` по проверенным связям PostgreSQL и отдельно загружает выбранную ветку. На desktop ветки раскрываются как плотное рабочее дерево, на телефоне используется последовательный drill-down с хлебными крошками.

В архиве можно выбрать до 30 текущих версий документов и выгрузить их одним ZIP общим исходным объёмом до 50 МБ. Сервер повторно проверяет сессию, `documents.read`, принадлежность каждого файла организации, размер и SHA-256; безопасные уникальные имена повторяют логическую структуру архива, а успешная операция записывается в audit log.

В карточке заказа доступна история всех его выездов. Лента строится из неизменяемых событий PostgreSQL и показывает создание, переносы, отмены и смены статуса с автором, временем, причиной и сравнением старого и нового состояния. При изменении даты, времени или длительности причина переноса обязательна в карточке заказа, адаптивном окне календаря и после drag-and-drop; она хранится отдельно от заметки и проверяется сервером и ограничением БД. Чтение ограничено текущей организацией; при очень длинной истории интерфейс явно сообщает, что показаны последние 500 событий.

Внутренний чат поддерживает общий офисный канал и закрытые группы. Пользователь с правом `chat.manage` может менять состав группы, но владелец сохраняется автоматически. К сообщению можно прикрепить один проверенный PDF, JPG, PNG, WebP, DOCX или XLSX до 15 МБ; скачать его сможет только текущий участник канала, после серверной проверки целостности.

В Docker системные напоминания синхронизирует фоновый worker, поэтому сотруднику не нужно предварительно открывать чат. Перенос выезда обновляет ещё не наступившее напоминание, закрытие акта, отмена выезда, продление или закрытие договора скрывают устаревшие сообщения. Локально worker можно запустить отдельно командой `npm run reminders:worker`, а транзакционную проверку идемпотентности и очистки — `npm run reminders:check`.

Раздел `Финансы` хранит счета, частичные клиентские оплаты и выплаты мастерам отдельными строками. Проведённые операции не удаляются: ошибочная оплата или выплата сторнируется с обязательной причиной, а неоплаченный счёт аннулируется. PostgreSQL блокирует переплату и автоматически пересчитывает выставленную, полученную и выплаченную суммы заказа. Полный браузерный сценарий проверяется командой `npm run finance:check` на запущенной CRM.

Администратор может подготовить перенос старых данных в `Настройки → Импорт`. Экран принимает пять независимых UTF-8 CSV по формату `CRM CSV v1`: клиенты, объекты, заказы, состав заказов и метаданные документов. Dry-run проверяет обязательные колонки, дубли, внешние связи, принадлежность объектов, существующие ИНН и номера заказов, а также сумму строк услуг. Исходные CSV и значения ячеек в журнале не хранятся; повтор того же пакета определяется по SHA-256 и возвращает прежний отчёт. На этом этапе рабочие таблицы не изменяются — реальное применение требует подтверждённой карты полей и тестовой сверки архива файлов.

Раздел `Сайты` в рабочем режиме использует PostgreSQL: администратор регистрирует домен и настраивает Метрику, GA4, Search Console или Яндекс Вебмастер. В браузер и audit log передаются только property ID и технический статус; вместо OAuth-токена форма принимает имя серверного секрета. Трафик за одну дату выбирается из одного канонического analytics-источника, поэтому параллельные GA4 и Метрика не удваивают посетителей, а поисковые показатели Google и Яндекса суммируются. Реальные запросы к API провайдеров начнутся после реализации worker и выдачи тестовых OAuth-доступов.

Повторяемая браузерная проверка dry-run удостоверяется, что клиенты, объекты, заказы, услуги и документы не изменились, а повторный запрос не создал второй import job:

```bash
npm run import:check
```

Рабочий CRUD сайта, защиту ссылки на секрет и адаптивность страницы можно проверить на запущенной CRM:

```bash
npm run sites:check
```

При запущенной CRM в `AUTH_MODE=required` полный браузерный поток можно проверить переменными `AUTH_CHECK_BASE_URL`, `AUTH_CHECK_IDENTITY`, `AUTH_CHECK_PASSWORD` и командой `npm run auth:check`. Проверка проходит атомарное мобильное оформление на 320 px, создаёт обычного клиента, объект, контакт и заказ, меняет статус, добавляет прямой расход, одиночный выезд и годовую серию, проверяет карточку мастеру, автосохранение и календарь, затем завершает сессию. Если отдельные `AUTH_CHECK_*` не заданы, локальная проверка использует bootstrap-учётную запись из `.env.local`.

## Проверки

```bash
npm run lint
npx tsc --noEmit
npm test
npm run build
```

При запущенном dev-сервере можно проверить 51 ключевое сочетание маршрутов, окон и viewport от 280 px до 4K:

```bash
npm run visual:check
```

В `AUTH_MODE=preview` интерфейс использует типизированные демонстрационные данные. В `AUTH_MODE=required` сотрудники и роли, клиенты, объекты, заказы, выезды, серии, календарь, задачи, документы, договоры, финансы, внутренний чат, аналитика и реестр сайтов читаются и записываются в PostgreSQL с серверной валидацией, tenant-проверками, audit log, idempotency, optimistic concurrency и ограничением пересечений расписания. Рабочее место мастера использует ресурсную фильтрацию по назначению и атомарно сохраняет закрывающий акт. Внешняя синхронизация сайтов и приём лидов остаются следующими отдельными интеграционными этапами.
